# OBS-001 Implementation Note

## Summary

Added readiness probing at `GET /health/ready` while keeping liveness at `GET /health` unchanged. Readiness checks PostgreSQL (`SELECT 1`) and Redis (`PING`), returns flat component JSON, and responds with 503 when any dependency is unreachable. Docker Compose API healthcheck now targets the readiness endpoint.

## Files Changed

| File | Purpose |
|------|---------|
| `app/infrastructure/health_checks.py` | DB and Redis probe helpers; builds readiness payload |
| `app/api/routes/health.py` | Added `GET /health/ready`; liveness unchanged |
| `tests/unit/test_health.py` | Liveness + readiness happy path and failure tests |
| `docker-compose.yml` | API healthcheck URL changed from `/health` to `/health/ready` |
| `tests/unit/test_compose_config.py` | Assertion updated for readiness healthcheck URL |
| `pyproject.toml` | Added explicit `redis` dependency for readiness probe |
| `stories/obs-001-health-check-endpoint.md` | Status set to `in_progress` |

## Behavior Added

- `GET /health` — liveness only; returns `{"status": "ok"}` with HTTP 200 (unchanged from INFRA-001).
- `GET /health/ready` — readiness; probes PostgreSQL and Redis on each request.
- Healthy response (200): `{"status": "ok", "database": "ok", "redis": "ok"}`.
- Unhealthy response (503): per-component `"error"` for failing probes; overall `"status": "error"`.
- Compose API service waits for readiness before marking the container healthy.

## Tests Added

## Decisions Made

- **Flat JSON schema** — Story AC uses flat `{status, database, redis}` keys. `docs/11-observability.md` and `docs/06-api-design.md` describe a richer nested schema; MVP intentionally uses the simpler shape per story acceptance criteria.
- **Liveness vs readiness split** — `/health` for process liveness (K8s liveness probe); `/health/ready` for dependency readiness (Compose/K8s readiness probe). Matches INFRA-001 deferral note.
- **Worker check deferred** — Story functional requirement lists worker connectivity as optional; deferred to **OBS-007** (background worker visibility). Readiness covers DB + Redis only for MVP.
- **Explicit `redis` dependency** — Added to `pyproject.toml` rather than relying solely on Celery's transitive `redis` extra.
- **Redis client lifecycle** — `check_redis()` closes the client in a `finally` block after `PING` to avoid connection leaks on repeated probes.
- **Silent probe failures** — Broad `except Exception: return False` is standard for health endpoints; structured logging of probe failures deferred to **OBS-002**.

## Known Limitations

- No Celery/worker connectivity check (OBS-007).
- No storage backend check (not required for MVP readiness).
- Unit tests mock probes; no Docker integration test against live postgres/redis in this story.
- Probe failures are not logged (OBS-002 follow-up).
