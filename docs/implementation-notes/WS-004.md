# WS-004 Implementation Note

## Summary

Implemented workspace member role change and removal via `PATCH /workspaces/{workspace_id}/members/{user_id}` and `DELETE /workspaces/{workspace_id}/members/{user_id}`. Owner and Admin can manage members using the same `_INVITE_ROLES` gate as WS-003. Admin cannot modify or assign Owner role. Last-owner protection returns `400 last_owner` when demoting or removing the sole Owner.

## Behavior Added

- `PATCH /workspaces/{workspace_id}/members/{user_id}` requires JWT and Owner/Admin membership.
- Request: `{ "role": "viewer" }` — same role validation as invite.
- Response `200`: `{ "user_id", "email", "role", "created_at" }`.
- `DELETE /workspaces/{workspace_id}/members/{user_id}` returns `204 No Content`.
- Target not in workspace → `404 member_not_found`.
- Viewer/Member/non-member caller → `403 forbidden`.
- Admin cannot PATCH Owner members or assign `owner` role → `403 forbidden`.
- Sole Owner cannot demote self (PATCH) or remove self (DELETE) → `400 last_owner`.
- Self-removal allowed when another Owner exists.
- Audit logging deferred to AUDIT-004/005.

## Decisions Made

- Reused `_INVITE_ROLES` frozenset from WS-003 for manage-member authorization (Owner/Admin).
- Last-owner protection uses `count_owners` repository query before demotion or removal.
- `400 last_owner` used per story requirement (API design doc listed 403; story overrides).
- Inline RBAC in service layer; centralization deferred to WS-005 `PermissionService`.
- DELETE returns `204` with no body per API design doc.
