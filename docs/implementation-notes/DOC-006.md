# DOC-006 Implementation Note

## Summary

Implemented `POST /workspaces/{workspace_id}/documents/{document_id}/reindex` with `DOCUMENT_MUTATE` permission enforcement. Re-index deletes existing chunks upfront, sets document status to `processing`, emits a minimal `document.reindex_requested` audit event, and enqueues a new ingestion job. Concurrent re-index attempts while the latest job is `pending` or `processing` return `409 reindex_in_progress`.

## Behavior Added

- `POST /workspaces/{workspace_id}/documents/{document_id}/reindex` requires Owner, Admin, or Member (`DOCUMENT_MUTATE`); Viewer receives `403 forbidden`.
- Workspace-scoped lookup: cross-workspace document id returns `404 not_found`.
- Deletes all `document_chunks` for the document before enqueueing a new job.
- Sets document status to `processing` before creating the ingestion job.
- Creates a new pending ingestion job (prior completed/failed jobs remain for history).
- Worker processes the new job by id; terminal-job skip applies only to the specific job row, not the latest guard.
- Emits audit event `document.reindex_requested` with `document_id` and `title` metadata (minimal AUDIT-003).
- Returns `202 Accepted` with `{ document, ingestion_job }`.

## Decisions Made

- Delete chunks synchronously in the API path per story requirements; worker still uses `replace_chunks_for_document` on success for idempotency.
- Concurrent guard checks only the **latest** ingestion job status (`pending`/`processing`), allowing re-index after `completed` or `failed`.
- Reuse upload response shape via dedicated `DocumentReindexResponse` schema for API clarity.
- Audit event uses `document.reindex_requested` per AUDIT-003; actor and IP persisted on audit row.

## Known Limitations

- Re-index steps (chunk delete, status update, audit, job create) are not one atomic transaction.
- No dedicated admin retry endpoint; failed documents must be re-indexed via this route (ING-007 deferred).
- Full audit query UI deferred to AUDIT-007.
