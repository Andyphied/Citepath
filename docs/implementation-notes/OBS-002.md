# OBS-002 Implementation Note

## Summary

Added structlog-based JSON logging and `RequestLoggingMiddleware` that emits one structured `request_completed` log line per API request, including `request_id`, `status_code`, `duration_ms`, and correlation fields (`user_id`, `workspace_id` when present on `request.state`).

## Files Changed

| File | Purpose |
|------|---------|
| `app/modules/observability/logging.py` | structlog configuration (JSON to stdout) |
| `app/modules/observability/request_logging.py` | `RequestLoggingMiddleware` |
| `app/main.py` | Register logging middleware; call `configure_logging()` |
| `pyproject.toml` | Add `structlog` dependency |
| `tests/unit/test_structured_logging.py` | Unit tests for logging config |
| `tests/api/test_structured_logging.py` | API tests for request-completion logs |
| `stories/obs-002-structured-logging.md` | Status set to `in_progress` |

## Behavior Added

- On app startup, `configure_logging()` configures structlog to emit JSON lines to stdout.
- Each completed HTTP request logs one info-level line with:
  - `timestamp`, `level`, `message` (`request_completed`)
  - `request_id`, `method`, `path`, `status_code`, `duration_ms`
  - `user_id`, `workspace_id` (null when not set on `request.state`)
- Middleware order: `RequestLoggingMiddleware` (inner) wrapped by `RequestIdMiddleware` (outer) so request IDs are available before logging.
- No request/response bodies, headers (except path/method), or auth tokens are logged.

## Tests Added

**Unit (`tests/unit/test_structured_logging.py`):**

- JSON output includes `level`, `timestamp`, and custom fields
- `configure_logging()` is idempotent

**API (`tests/api/test_structured_logging.py`):**

- `GET /health` emits log with client `request_id` and `status_code` 200
- `GET /auth/me` 401 emits log with `request_id` and `status_code` 401

## Decisions Made

- **Library:** `structlog` with `JSONRenderer`, `EventRenamer("message")`, and stdlib `LoggerFactory` (JSON lines to stdout via `logging.basicConfig`, compatible with pytest capture).
- **Middleware placement:** Registered before `RequestIdMiddleware` so request ID context is set on ingress before the logging middleware completes the request.
- **Domain event logging deferred:** Ingestion, retrieval, and LLM call log lines are not implemented (those modules do not exist yet). Follow-up when ING/RAG/usage stories land.
- **user_id / workspace_id:** Read from `request.state` when present; remain null until route dependencies populate them (future enhancement).

## Known Limitations

- No ingestion, retrieval, or LLM domain log events yet.
- `user_id` and `workspace_id` are typically null in middleware logs until handlers/deps set `request.state`.
- Worker/Celery job logs not covered (separate story scope).
- No log redaction middleware beyond omitting sensitive fields by design.
