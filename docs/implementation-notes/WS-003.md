# WS-003 Implementation Note

## Summary

Implemented workspace member invitation via `POST /workspaces/{workspace_id}/members`. Owner and Admin can invite registered users by email with a workspace role. Viewer and Member receive `403`. Unknown email returns `404`; duplicate membership returns `409`.

Gate 1 scope covers invite (`POST`) only; role change and removal (`PATCH`/`DELETE`) deferred to WS-004.

## Behavior Added

- `POST /workspaces/{workspace_id}/members` requires JWT and Owner/Admin membership.
- Request: `{ "email": "eng@example.com", "role": "member" }` — email validated as `EmailStr` and normalized to lowercase.
- Valid roles: `owner`, `admin`, `member`, `viewer`.
- Response `201`: `{ "user_id", "email", "role", "created_at" }`.
- Invitee must be a registered user; unknown email → `404 user_not_found`.
- Already a member → `409 already_member`.
- Non-member caller or insufficient role (Viewer/Member) → `403 forbidden`.
- Admin cannot assign `owner` role → `403 forbidden` (per security matrix).
- Unauthenticated → `401 unauthorized`.

## Decisions Made

- Inline Owner/Admin role check in `WorkspaceService.invite_member` using `_INVITE_ROLES` frozenset; documented for centralization in WS-005 `PermissionService`.
- Admin cannot assign `owner` on invite, consistent with `docs/09-security-and-rbac.md` permission matrix.
- Email lookup via existing `UserRepository.get_by_email` (normalized lowercase).
- Duplicate detection in service layer before insert; repository `IntegrityError` maps to `AlreadyMemberError` as safety net.
- Non-member workspace access returns `403` (consistent with WS-002 workspace endpoint semantics).

## Known Limitations

- No centralized `PermissionService` (WS-005).
- API tests require Docker (testcontainers); skipped when Docker unavailable.
